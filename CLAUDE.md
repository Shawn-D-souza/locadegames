# Locade Games

A platform of online multiplayer mini-games: real-time action games (2D now, maybe 3D later) and turn-based games. Web first; an Android app comes later.

> **This file is the single latest source of truth for the platform** (everything shared by all games). Each game's own rules, decisions, look and files live in its doc in [`docs/games/`](docs/games/) (see [Games](#games)). Whenever a decision, service, plan, file or folder changes, update the relevant section here or in the game's doc in the same change. The docs hold decisions and how things work, **not progress** (owner decision): nothing about what is committed, pushed, deployed or tested where, and no "last updated" dates; git history and the Cloudflare dashboards already show that. The project owner's latest direction takes precedence over anything in these files; when they conflict, the file must be updated to match. Visual design lives in [`DESIGN.md`](DESIGN.md).

## Rules

1. **Free tiers only until the platform earns money.** Don't add anything that costs money.
2. **Best value long-term.** As soon as revenue covers it, move to the cheapest option per player, even if that means leaving the current platform.
3. **No peer-to-peer.** Server-authoritative multiplayer only.
4. **Online setup goes to the owner.** When something needs setting up online (accounts, dashboards, settings, deploys), give the owner clear step-by-step instructions instead of assuming it's done.
5. **Run `npm run check` once a piece of work is finished** (typecheck + lint + build in one go), not after every code change, and fix what it finds before reporting done. Don't run `typecheck`, `lint` or `build` separately.
6. **No attribution lines in commits or PRs** (owner decision): no `Co-Authored-By`, `Claude-Session` or "Generated with" lines.

## Architecture

- **Portable game logic.** Rules, physics and the tick loop are plain TypeScript with no Cloudflare-specific code. Only a thin adapter connects them to Durable Objects, so the same logic can later run on Node.js with minimal changes.
- **Shared logic.** Game logic is shared between client and server.
- **One Durable Object per region** runs many matches (not one per match) to save free-tier compute.
- **Real-time games (arena format):** everyone in the room plays **one match together** (not a tournament). The host's start makes a `RoomRecord.arena` (entrants, `startsAt` = now + the countdown, `endsAt`, arena size); the region DO runs the match in memory (`ArenaService`, with one match class per game in `src/server/arena/`) and, when it ends, writes the ranking (`ArenaResult`: place, land share, time survived, quit) and the champions (place 1; ties share the title and each gets a trophy). If the DO restarts mid-match the match is lost and the room goes back to its hub (`abandonArena`).
  - Server-authoritative: clients send inputs; the server steps at a fixed rate (~20 steps/s, a `setInterval` in the DO only while a match runs, so the DO hibernates otherwise) and sends a snapshot every step; a full sync goes out on join, reconnect or a client's `sync` request (gap in steps, tab woke up).
  - Game traffic is **binary WebSocket frames** (each game's `wire.ts` on `src/shared/protocol/bytes.ts`); room messages stay JSON. Inputs are sent only when they change, at most one per step.
  - Client: a server clock from min-RTT pings; your own player predicted ahead with the same simulation code as the server (inputs stamped with the step they apply on, so both agree exactly); others interpolated a little in the past; small corrections eased out. Lag compensation is decided per game (Territory: none, favour the victim). Each game's doc has its details.
- **Real-time 1v1 games (a tournament played live; Head Crash):** the catalog says `format: "tournament"` with `play: "live"` (turn-based games say `play: "turns"`). Pairing, rounds, points, byes and titles are the tournament's, unchanged; only the match differs: its record holds just a score (`LiveMatch`), there are no moves or turn timers, and the region DO plays it in memory (`DuelService` in `src/server/duel/`, one match class per game) and reports each point (`scoreLiveMatch`) and the end (`finishLiveMatch`).
  - A round's matches run side by side; each is streamed (binary) only to its two players and whoever watches it (`RoomTransport.sendBinaryToMany`; a watcher sends `watch` / `unwatch`).
  - After every change to a room, `DuelService.reconcile` makes what runs match what the record says is live: a new round starts its matches (at the round's shared start), a quit or the end stops them. A match lost to a DO restart is started again from its recorded score when a player's next frame arrives (unlike an arena match, it is not abandoned).
  - `ArenaService` and `DuelService` share the host's one timer through `TickerHub` (it runs at the quicker pace asked for, only while a match of either kind runs).
  - Client: its own lazily loaded screen instead of `MatchScreen`; the round intro shows GET READY! (the game counts its own 3, 2, 1). Netcode is decided per game (Head Crash plays the whole match ahead and blends corrections out; its doc has the details). The server clock from pings is shared (`src/web/netcode/serverClock.ts`).
- **Turn-based games:** no tick loop. The server validates moves and lets the Durable Object hibernate between turns.
- **Low traffic:** batch inputs; use small binary messages instead of JSON for action games. Turn-based games use small JSON messages.
- **Platform first, room first.** Home is only name + CREATE ROOM + JOIN WITH CODE (no game list there; it confused). A room is a session: friends gather, the **host picks a game** (others tap a game to *suggest* it; their avatars show on its tile), they play, return to the room, pick another. Games are listed in `src/shared/games/catalog.ts` (id, name, min players, `format`: `tournament`, played in `turns` with a turn time or `live`, or `arena`) with turn-based rules in `src/shared/games/registry.ts` (`MatchGame` interface in `games/types.ts`); client visuals in `src/web/games/gameLooks.ts`. Adding a turn-based game = catalog entry + `MatchGame` rules + tile art + its match look (`MATCH_LOOKS` in `src/web/games/matchLooks.ts`: its board, on the shared `BoardFrame`, how wide the match screen gets for it, and the sounds each move makes) + its doc; a live tournament game = catalog entry + its simulation + a match class in `src/server/duel/` + its screen (routed from `RoomScreen`) + its doc; an arena game = catalog entry + its simulation + a match class in `src/server/arena/` + its screen + its doc. Every game also gets its sounds (`src/web/games/<game>/sounds.ts`, added to `soundBook.ts`), its haptics (`src/web/games/<game>/haptics.ts`, added to `hapticBook.ts`, with rows in `soundHaptics.ts`) and a playtest flow in `scripts/playtest/`.
- **Private rooms only, up to 8 players** (`ROOM_CONFIG.maxPlayers`; premium may raise it to 12 later; never unlimited: cost grows with room size, one region DO, screen space). Players share the 6-digit code, shown as `482 913` (or the `?room=CODE` link). Digits only (owner decision): phones show the number keypad and codes are easy to read aloud; 6 digits (not 5) keep 100,000 codes per region so strangers can't easily guess a live room. No quick match or random matchmaking.
- **Fair starts** (owner decision: every game must be fair). Being the host, joining first or ranking higher never gives you the better turn or seat. Over a game, everyone gets the advantage (moving first) as evenly as possible, and when it can't be split evenly it goes to a random player. Nothing new on screen: players just see who starts. How it's done: the server picks a random number once per game (`coinSeed`, `crypto.getRandomValues` in `RoomService`) and the pure logic uses it (`coinFlip(coinSeed, matchId)` in `tournament.ts`), so it stays testable. The same rule sets the whole turn order whatever the number of players in a match: whoever has gone first least goes earlier, ties in random order.
- **Every 1v1 game is a Swiss-style tournament**, turn-based or real time (catalog `format: "tournament"`; owner decision: draws are a normal result, so no knockouts, replays or thinking-time tiebreaks; pure, in `src/shared/tournament/`). Everyone plays every round; matches in a round run at the same time and whoever is free watches any live match. Pairing, byes, points and titles never depend on chance (owner decision; games themselves may use dice or luck); only who starts can (see **Fair starts**):
  - Points (`TOURNAMENT_CONFIG`): win 2, draw 1, loss 0, bye 2 (sitting out counts as a win).
  - Rounds: `roundsFor(players)`: 2 players → 1 match, 3–4 → 2 rounds, 5–8 → 3 (same as a knockout would need).
  - Seeding: most session trophies, then earliest joiner. Round 1: best seed meets the weakest. Later rounds: ranked by points (then seed), each player meets the next one they haven't played (a rematch only if nothing else fits).
  - Who starts (seat 0): whoever has started fewer games in this tournament, else picked at random (**Fair starts**).
  - Round break (owner decision: everyone enters a round together and it starts at one exact moment): a round after the first gets one shared `startsAt`, `TOURNAMENT_CONFIG.roundBreakMs` (7 s) after the previous round ends. Moves before it are refused and the turn clock starts then. Phones show their own result first (4 s), then the round intro with a countdown, all keyed to that server time, so every match of the round begins at once. No server timer is needed.
  - Byes (odd players): the lowest-ranked player who hasn't had one yet.
  - Champions: most points after the last round. Players level on top points **share the title** (owner decision) and each gets a room trophy. A drawn 2-player match = both champions.
  - Turn timer (turn-based games): `turnTimeMs` per move (set per game in the catalog; see its doc; the countdown shows only in the last 5 s); on expiry the game's deterministic `autoMove` is played. The server has no timers (so it can hibernate): clients in the match (or watchers if both players are away) send `timeout` claims after the deadline and the server checks its own clock.
  - Only players in the room when the host starts take part; anyone joining later watches and plays the next game.
  - Quitting (owner decision: the ✕ on the match screen or the phone's back button, after a confirm) forfeits your live match (the opponent gets the win) and takes you out of the rest of that game, but you **stay in the room** to watch and play the next one (`quit` message). Leaving the room (back on the points screen) does the same and then leaves. Either way you keep your points in the table, greyed, but are not paired again and can't be champion. Results show a champion card and the final points; the host picks PLAY AGAIN or BACK TO ROOM (everyone), and another player's back arrow takes only them to the room (owner decision: no LEAVE button on results).
- **One Worker deployment (`locade-server`).** It holds the matchmaking routes, the usage cron and the `RegionServer` Durable Object class. Folders keep them separate (`src/server/matchmaking`, `usage`, `rooms`).
- **Region in the room code.** The first digit of a code names the region (`1` wnam, `2` enam, `3` sam, `4` weur, `5` me, `6` apac, `7` oc, `8` afr). The other 5 digits are random. No duplicate codes: the region DO checks and stores a code in one synchronous step and refuses one it already has; the Worker then tries a fresh code (`claimRoomCode`, up to `maxCodeAttempts`). A joiner reaches the creator's region DO with no lookup. The region DO is `getByName("region:<hint>", { locationHint })`; the region comes from `request.cf` continent/longitude.
- **Request flow.** `POST /api/rooms` (no body, so no CORS preflight) checks capacity and creates the room over DO RPC. `GET /api/rooms/:code/ws` forwards the WebSocket upgrade to the region DO. Every action after that is one WebSocket message (DO requests bill at 20:1). Keepalive `ping`/`pong` uses `setWebSocketAutoResponse` and costs nothing.
- **Player names.** No accounts yet. On the first visit the client makes a random name ("Brave Otter", `src/web/utils/randomName.ts`) and saves it in `localStorage` once, so it never changes. It fills the name field for new players; if the field is left empty, that name is used, so nobody is blocked from playing. A typed name is remembered too.
- **Room state** is one JSON row per room in DO SQLite (players, host, phase, current tournament or arena summary; a live arena's simulation stays in memory, never in SQLite). Each player has an id (0–7, also their color) reclaimed after a disconnect with a per-player token kept in the tab's `sessionStorage`. If the token is gone (a sleeping phone often drops the tab's storage, or the link was reopened), joining with **the same name as an away player** takes that seat back: color, points and live match (owner decision: never a second seat for the same person; a connected player's seat is never taken). A phone waking up or coming back online reconnects at once. Room views carry `serverNow` so clients can draw turn timers. Rooms empty for more than 1 h, or older than 24 h since creation even if in use (owner decision: nobody plays 24 h straight; it also clears rooms left open in a tab), are swept lazily when rooms are created (no alarms).
- **Portable room layer.** `roomLogic.ts` holds pure reducers. `RoomService` talks only to the `RoomStore` / `RoomTransport` ports. `RegionServer` + `SqliteRoomStore` + `HibernationTransport` are the Cloudflare adapter; a Node.js host only needs new port implementations.
- **Haptics.** What they feel like is in DESIGN.md, Haptics. A feel is a named entry in a book (`defineHaptics`: what it's for in plain words, its pulses at `selection` / `light` / `medium` / `heavy`, the same names as `@capacitor/haptics`); a wrong name is a compile error. **Feels follow sounds:** `soundHaptics.ts` says what each sound feels like, and `playSound` / `playSoundSequence` play that too (even with sound off), so feels land on the same moments and move with the animations, with nothing to call in screens or hooks. Only the marks of a board game are called directly (`playHaptic`), since it depends on whose mark it is. A whole moment becomes one pattern, because a new vibration cuts off the last; a single pulse never cuts a running pattern. `hapticPlayer.ts` is the only thing that touches the motor, and the one file the Android app changes. **What a phone can do decides how much it feels:** Android browsers feel everything; on an iPhone, Apple only allows a tick from a real finger tap since iOS 26.5 ([WebKit PR](https://github.com/WebKit/WebKit/pull/65327)), so iPhones feel taps on buttons and board cells (`ref={hapticTarget}` on `PillButton`, `IconButton`, `GameTile`, `Toggle`, `BoardCell`, `UltimateCell`, `MatchCard`: an invisible switch on top of the button; CSS in `global.css` hides it when disabled or switched off; not on buttons that are held, like Head Crash's drive buttons) and no game events. web-haptics is never called on iPhones. On by default; the switch in Settings shows only on phones that can feel it (kept in `localStorage`). Haptics stay out of simulation, netcode and server. `tests/haptics.test.ts` checks every feel automatically. Adding a game's haptics: `src/web/games/<game>/haptics.ts`, one line in `HAPTICS` (`hapticBook.ts`), and a row in `soundHaptics.ts` per sound that's felt.
- **Sound.** Sound effects only for now (owner decision: no music); what they sound like and how loud is in DESIGN.md, Sound. A sound is a named entry in a book (`defineSounds`: what it's for in plain words, its level, how much room, how it's built from the kit in `src/web/sound/kit/`); the name says what it's for and a wrong name is a compile error (`playSound("mainButtonPress")`). Sounds are pure functions of their name and take (seeded), rendered at a fixed `SOUND_SAMPLE_RATE` (32 kHz) **when the site is built, never on the phone** (owner decision: a phone's time goes to the game's frames): `scripts/soundFilesPlugin.ts` makes every take an 80 kbps MP3 in `assets/sounds/` (named by its content's hash, so `_headers` lets phones keep them for good) and lists them as `virtual:sound-files`; in development it serves them from memory and makes them again when a sound changes. Each file starts with a marker click the player finds after decoding (MP3 decoders add different amounts of silence at the start), so every sound starts on its exact sample and loops are seamless (`sound/files.ts`). The platform's files download once the page has loaded and are decoded (by the browser, off the game's thread) on the first touch; a game's when that game starts (`prepareGameSounds`, ahead of the rest; **so the cost per visit doesn't grow with the number of games**). A sound asked for before its file is in plays if it arrives within 250 ms, or is skipped. `soundPlayer.ts` is the only thing that touches Web Audio. Which sound plays when is decided by pure functions (`src/web/sound/cues/`, each game's `territoryCues.ts`), timed from the theme's motion tokens so sounds move with the animations; screens and components only call the player. Sounds stay out of simulation, netcode and server. Sounds are on by default, with a switch and a volume slider in Settings (kept in `localStorage`; the volume starts at 100, which is every sound as made, and sets the gain every sound passes through, on a squared curve so its steps sound even; `sound/volume.ts`). Adding a game's sounds: `src/web/games/<game>/sounds.ts`, one line in `GAME_SOUNDS` and one in `SOUNDS` (`soundBook.ts`). `tests/sound.test.ts` checks every sound automatically (level, length, no clipping, ending cleanly).
- **Security.** Origins are checked against `ALLOWED_ORIGINS` for both HTTP and WebSocket. The server validates every message, turn and seat, sanitizes names and caps message size.

## Free-tier protection

- The Workers Free plan has daily limits, and operations fail once they're exceeded. Limits reset at **00:00 UTC**:
  - 100,000 Worker requests
  - 100,000 Durable Object requests
  - 13,000 GB-s of DO duration
  - 5M SQLite rows read
  - 100,000 SQLite rows written
- A **cron trigger every 10 min** (`src/server/usage/checkUsage.ts`) queries the GraphQL Analytics API for today's account-wide totals. It runs one query per metric, so a renamed field only disables that one metric. The result goes to KV key `usage-status`.
- Room creation reads that status (cached 60 s per isolate) and **stops creating rooms at 85%** of any limit. Running rooms and rematches finish normally. If the analytics call fails, the previous status is kept; a `full` status expires on its own at `resetAt`.
- **Real-time matches cost more:** the DO stays awake (duration) while a match runs, and every input message is a DO request. Each real-time game's doc records its measured cost; watch the DO request and GB-s numbers once people play them.
- Players see a friendly **"Servers full, back at [time]"** screen (time shown in their local timezone) instead of errors. If the Worker is already over the hard limit (fetch fails with no CORS headers) and the browser is online, the client shows the same screen with the next 00:00 UTC.
- Limits and the 85% threshold live in `src/server/config.ts` (`FREE_TIER`). Secrets: `CF_API_TOKEN` (Account Analytics: Read) and `CF_ACCOUNT_ID`.

## Code standards

- **Code map.** Keep the [Code Map](#code-map) below listing every shared folder and key file with its purpose, and each game's doc listing that game's files, so code is found without searching. Update them whenever files are added, moved or removed.
- **Single-purpose files.** One component per file. Split by responsibility, not line count: a file doing more than one job should be split; ~400 lines is a signal to check.
- **Separation of concerns.** Screens compose; components render; hooks hold stateful logic; services talk to the outside world (network, storage); utils are pure functions. In games, simulation, networking and rendering never mix.
- **No magic values.** Colors, spacing, radii and typography come from the theme in `src/theme/` (derived from `DESIGN.md`), never hard-coded. Gameplay numbers (tick rates, speeds, sizes, limits) live in each game's config.
- **Styling: Tailwind first, CSS where it reads better** (owner decision). Components style themselves with Tailwind classes (`clsx` for conditions; no CSS Modules). Tailwind's own default theme is not loaded: `src/theme/tailwind.ts` turns our tokens into the whole theme, so only on-theme classes exist (`bg-ink`, `p-4`, `rounded-card`, `text-caption`, `min-h-tap`, `bg-player` for the player's color) and `npm run check` fails on unknown, conflicting or duplicate classes and on class order (`eslint-plugin-better-tailwindcss`; `npx eslint --fix` sorts them). Write CSS in `src/web/styles/` only where it reads better than classes: keyframes (`animations.css`, used as `animate-*`), visual recipes as `@utility` (`utilities.css`), base styles (`global.css`). Class lists kept in a constant are named `..._CLASSES`, so the lint rules check them too. No conflicting classes instead of overrides (pick one with a ternary).
- **Testing (the usual pyramid).** Unit tests (Vitest) for rules and logic: fast, run often. `npm run playtest <game>` once a fix that changes what players see or how a game flows is done, for the game being worked on; `npm run playtest` (every game) before a push. Dev preview pages (`?preview=...`) jump straight to a moment (an ending, a knockout) to check a look without playing. The owner tests on real phones.
- **Deterministic game logic.** Simulation is pure: state + inputs → new state, fixed timestep, seeded RNG, no I/O or timers, so client prediction and the server agree.
